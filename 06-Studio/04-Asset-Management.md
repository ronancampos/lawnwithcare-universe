# 🌱 Lawn With Care Universe

# Asset Management

> "An asset only has value if it can be found, understood and reused."

---

# Purpose

This document defines how every asset within the Lawn With Care Universe is organized, stored, named, versioned and maintained.

The objective is to ensure that every file remains discoverable, reusable and consistent throughout the life of the franchise.

---

# Asset Philosophy

Every asset should have:

One location.

One purpose.

One owner.

One current version.

The repository should always represent the latest approved state of the project.

# Repository Rule

Every asset exists only once.

Duplicate files should never become the source of truth.

---

# Folder Philosophy

Folders organize by purpose.

Never by software.

Correct

```
Characters

World

Storytelling
```

Incorrect

```
Photoshop

PNG

Illustrator

Final
```

The repository describes the universe.

Not the tools.

---

# File Naming

Use descriptive names.

Avoid spaces.

Use hyphens.

Examples

```
Brooks-Visual-DNA.md

Sprout-Identity.md

S01E003-Storyboard.pdf

Discovery-Band.svg
```

---

# Episode Naming

Official format

```
S01E001
```

Examples

```
S01E001-Story.md

S01E001-Storyboard.png

S01E001-Dialogue.md

S01E001-IG-Carousel.pdf
```

---

# Image Naming

Format

```
Character-Description-Version
```

Example

```
Brooks-Front-v1.png

Sprout-Expression-Happy-v2.png

Discovery-Band-Reference-v1.png
```

---

# Prompt Storage

Every approved AI prompt should be stored.

Recommended structure

```
05-AI/

Prompts/

Characters/

World/

Storytelling/

Marketing/
```

Prompts are production assets.

Not temporary conversation text.

---

# Master Assets

Some files become master references.

Examples

Brooks Turnaround

Sprout Turnaround

Official Logo

Discovery Frame™

Discovery Band™

Field Kit

These assets should never be edited directly.

Create new versions instead.

---

# Working Files

Working files remain editable.

Examples

Storyboard

Draft Dialogue

Concept Sketch

These files may evolve until publication.

---

# Published Assets

Published assets are read-only.

Examples

Final PDF

Final PNG

Final Episode

Approved Character Guide

They become historical records.

---

# Version Structure

Recommended

```
v0.1

Concept

↓

v0.5

Working

↓

v0.9

Review

↓

v1.0

Published
```

Minor updates

```
v1.1

v1.2

v1.3
```

Major redesign

```
v2.0
```

---

# Asset Metadata

Whenever possible include:

Title

Author

Date

Version

Status

Related Documents

Related Characters

Keywords

This improves discoverability.

---

# Source Files

Always preserve editable originals.

Examples

PSD

AI

SVG

Figma

Blend

Do not rely only on exported files.

---

# Export Files

Store separately.

Examples

PNG

PDF

JPG

WEBP

MP4

Exports should never replace source files.

---

# Archive Policy

Nothing important is deleted.

Deprecated assets move to:

```
Archive/
```

The archive preserves project history.

---

# Canon Assets

Assets considered CANON should include:

```
status: CANON
```

inside their metadata.

---

# Temporary Assets

Temporary assets belong in:

```
Work-In-Progress/
```

They should never remain indefinitely.

---

# Reference Assets

References include:

Mood boards

Real photographs

Scientific references

Plant references

Lighting studies

These are inspiration.

Not canon.

---

# Asset Relationships

Every asset should reference related files.

Example

```
Brooks-Visual-DNA

Related

Brooks-Canon

Brooks-Prompt-Master

Field-Equipment

Story-Bible
```

The repository should behave like a connected knowledge graph.

---

# Backup Strategy

Maintain at least:

Working Copy

↓

Git Repository

↓

Cloud Backup

No asset should exist in only one location.

---

# AI Assets

AI-generated files should include:

Generation date

Prompt version

Model used

Human edits (if any)

This preserves reproducibility.

---

# Searchability

Anyone should locate an asset using:

Character

Episode

Location

Object

Season

Badge

Document type

Good naming reduces friction.

---

# Asset Lifecycle

Every asset follows:

Idea

↓

Draft

↓

Review

↓

Approved

↓

Published

↓

Archived

This lifecycle applies to every file in the project.

---

# Repository Health Checklist

Regularly verify:

✓ Duplicate files removed

✓ Naming consistent

✓ Versions updated

✓ Canon assets identified

✓ References connected

✓ Archive organized

✓ Working files cleaned

✓ Metadata complete

---

# Long-Term Vision

The repository should remain understandable even years from now.

A new contributor should be able to locate any asset in minutes without prior knowledge of the project.

The organization should scale naturally as the franchise grows.

---

# Official Asset Principle

Every asset should be easy to find.

Easy to understand.

Easy to reuse.

Easy to trust.

Documentation turns files into knowledge.
